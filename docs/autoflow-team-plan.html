AutoFlow

Team Work Plan

Building the full system — 7 people, 4 weeks, end‑to‑end
This plan divides the complete AutoFlow system — frontend, backend, and testing — among 7 team members. The goal: everyone has a roughly equal share, nobody’s work blocks or breaks anyone else’s, and the pieces snap together cleanly at the end.

Starting point: the new UI (UiUx‑New) is already built with mock data.

Remaining work: build the backend and connect the UI to real data, feature by feature.

Backend: FastAPI  ·  Frontend: React (existing)  ·  Timeline: 4 weeks

How the Work Is Divided

We split the system into 7 vertical slices. Each person owns one complete feature — its database tables, its backend API, its frontend wiring, and its tests. One feature, one owner, top to bottom.

Why slices, not layers

If we split by layer — “one person does all frontend, another does all backend” — everyone ends up editing the same files at the same time. That means constant merge conflicts and one person waiting on another all day.

With vertical slices, each person works inside their own folder. Two people rarely touch the same file, so their work never collides. Think of it like 7 builders each finishing a different room of a house instead of all crowding into the kitchen.

Phase 0 — Sprint 0: Foundation

Week 1, Days 1–3  ·  whole team together

Sprint 0 is infrastructure, not features. It is the foundation, the pipes, and the wiring in the walls — no rooms or furniture yet, but every feature later plugs into it. Nobody starts their own slice until this is finished. With only 4 weeks, this is kept tight — 3 days, not a full week.

Why do this as a shared step: if all 7 people set up their own backend and pick their own table names, nothing connects. Three days of shared setup means all 7 slices snap together cleanly later. To stay on time, all 6 items below run in parallel on Days 1–3, not one after another.

The 6 deliverables

ItemTypeWhat it is
Repo structureSetup One repository, two folders: frontend/ (the existing UiUx‑New moves here) and backend/ (new FastAPI project).
Backend skeletonSetup An empty FastAPI app that simply starts up. PostgreSQL database, SQLAlchemy + Alembic for tables, and Docker Compose so every machine runs the exact same setup. No real endpoints yet.
Frozen API contractDocument The most important deliverable. A written list of every endpoint — its URL, what data goes in, what data comes back. It is a document, not code. Once agreed, it is frozen.
Shared data modelSetup Agree on the core shared tables: workflows, steps, parts, users, expenses. Just the columns — no business logic.
AuthSmall feature A working login. This is the only bit of real functionality in Sprint 0, because every other slice needs to log in to be tested. Roles can stay loose for now.
CI pipelineSetup A config that automatically runs lint and tests on every push, so broken code is caught early.
In short: 5 of the 6 items are pure setup. Only Auth is a small piece of real functionality. All the actual features — creating workflows, pricing parts, finance, PDF extraction — are built in Phase 1.

Who leads what in Days 1–3

The whole team works on Sprint 0 together, but to avoid chaos each item has one lead while others pair in:

  • P1 — leads repo structure, backend skeleton, CI pipeline, and auth.
  • P2, P5 — lead the frozen API contract (they touch the most endpoints).
  • P3, P4, P6, P7 — lead the shared data model and review the API contract for their own slice.

Order of Completion

Some slices depend on others, so the order matters. Anyone waiting on a dependency does not sit idle — they build against the frozen API contract using a stub, then swap in the real data later.
WEEK 1 · DAYS 1–3 Foundation

Whole team builds Sprint 0 together — the shared skeleton. Kept to 3 days. No feature work starts yet.

WEEK 1 DAY 4 – WEEK 2 First wave — the dependencies

P1 P4 Everything else needs these, so they start the moment Sprint 0 ends. P1 builds the workflow engine; P4 builds the parts catalog. No workflow can move without P1, and no part can be priced without P4.

WEEK 2 – MID WEEK 3 Second wave — build on the base

P2 P3 P5 Job board, intake, and pricing start mid‑Week 2 — first against stubs, then on the real first‑wave APIs as they land. P5’s pricing locks onto P4’s parts catalog as soon as it is ready.

MID WEEK 3 – WEEK 4 Third wave — the back half

P6 P7 Close‑out needs P5’s approval done. Finance needs P5’s pricing done, since profit is calculated from the quoted price.

WEEK 4 · LAST 3 DAYS Integration + Testing

All 7 slices are wired together, the seams where features meet are tested, bugs fixed, and the whole system polished. With 4 weeks, integration and testing run as one combined push.

Rules That Keep Work From Colliding

The whole plan only works if everyone follows a few simple ground rules. They exist so that one person’s work can never break another’s.

1. One feature folder, one owner

Each person works only inside their own feature folder. Do not edit another person’s folder — if you need a change there, ask them. This is what guarantees two people never overwrite each other.

2. Shared files change carefully

A few files are shared by everyone — routing, the API contract, common types. These change only through a small, reviewed pull request, approved by whoever owns that shared file.

3. The API contract is frozen

Once Sprint 0 ends (Day 3), the list of endpoints and their data shapes does not change casually. If a change is truly needed, it is discussed with the team first — because someone else may be building against it.

4. Every slice ships with its own tests

There is no separate “tester” person. The owner of each slice writes the tests for that slice. Everyone is multi‑talented — frontend, backend, and testing are all part of owning a feature.

5. Don’t sit idle on a dependency

If your slice is waiting on another, build against the frozen API contract with a stub (fake data in the agreed shape). When the real backend is ready, you simply swap it in — no time lost.

6. Daily 15‑minute sync

A short daily check‑in to flag when one slice is about to unblock another, and to catch problems early.
